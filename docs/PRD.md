# ModernTavern 产品需求文档

版本：0.3 · 更新日期：2026-10-20 · 状态：业务边界收敛，技术方案与部分边界待验证，尚未实现

本文记录本轮访谈已确认的产品决策，作为 MVP 设计与验收依据。未决事项明确列出，不将助手建议视为用户批准，也不将本次文档提交视为代码实施授权。后续决策变更应同步更新本文。

## 1. 产品目标

构建受 SillyTavern 启发的现代 RP 聊天产品，重点改善长文本阅读、文字输入输出、剧情控制和复杂功能的组织方式。

首版以用户本人的日常 RP 使用作为验收依据。产品采用 VPS + 浏览器、单用户自托管方式，支持多个设备同时登录，优先保证移动端浏览器体验。通过 Docker 简便部署，适合公网使用；不开发原生客户端。

视觉目标是现代、简洁、柔和且清晰；操作应避免误触生成、打断阅读或丢失输入。角色设定与外部文本之间的具体复制流程暂缓细化，MVP 先提供原始 Markdown 复制。

## 2. 范围与优先级

### 2.1 MVP 必须具备

- 原生聊天闭环：新建、打开、保存、重命名、删除会话及按名称搜索；发送消息、流式生成、停止、继续、重新生成。
- 单个会话的自有格式导入导出，保留全部候选与选中状态；不提供全部会话打包导出。
- 消息编辑、删除及其明确的后续影响；会话末尾 AI 消息的 Swipe 候选管理；显式独立分支。
- 后端持有生成任务，浏览器关闭或断线不取消生成；重连同步已保存内容与任务状态。
- 同一账号多设备同时登录；不同会话并行生成，同一会话最多一个生成任务。
- 多套 OpenAI 兼容连接配置的新增、编辑、删除、切换与模型选择。
- 阅读式与气泡式切换、多套主题配色、亮色／暗色／系统模式、字号和正文宽度设置。
- 移动端友好输入、阅读、浮框与操作入口。
- Docker 部署、首次设置单一账号密码、禁止开放注册。

### 2.2 后续阶段

- 角色卡、世界书、预设的管理与相关业务功能。
- 角色卡、预设、世界书的自有格式导入导出，以及聊天记录和上述内容的 SillyTavern 兼容导入导出，随对应后续功能交付；具体版本、格式与保真范围尚未确定。
- 上下文总预算与最大输出量由预设管理；MVP 暂用固定默认值，不增加连接配置中的预算编辑入口。

### 2.3 MVP 不纳入

- 原生客户端、多人账号服务、开放注册。
- 专门的角色／场景／系统提示词编辑入口；设定直接作为普通聊天消息发送。
- 滑动手势切换 Swipe、纯文本复制选项、自动故障重试。
- 未经确认的功能，例如原版 JS 扩展兼容、自动记忆、自动摘要、Agent 编排。它们不构成默认交付要求。

## 3. 核心概念

| 概念 | 产品语义 |
|---|---|
| 会话 | 一条有序的消息历史，可独立生成、命名和恢复阅读位置 |
| 消息 | 用户输入或 AI 回复；AI 消息可以持有多个候选 |
| Swipe 候选 | 同一 AI 消息的不同回复版本，保留当前选中状态 |
| 重新生成 | 为会话末尾 AI 消息请求新候选，不覆盖或删除旧候选 |
| 继续 | 不发送新用户消息，沿当前剧情生成一条新的 AI 消息 |
| 分支 | 截至指定消息的完整独立副本，包含该消息及历史候选与选中状态 |
| 连接配置 | API 地址、凭据、模型选择等连接信息；不是 SillyTavern 预设 |
| 生成任务 | 后端管理的一次模型请求，不依赖浏览器连接存活 |

以上是行为定义，不规定数据库表结构或实现方式。

## 4. 会话、消息与剧情操作

### 4.1 消息和候选

- 只有会话末尾为 AI 消息时，该消息才可直接切换、重新生成或删除 Swipe；其后已有用户消息就不可直接操作候选，历史位置通过分支探索。
- 失败属于 AI 回复／生成任务，不属于用户消息。失败后重新生成新增 Swipe，保留原候选。
- 无输出的失败或停止也保留空候选及其状态。新候选即使中途失败仍保持选中，用户可手动切回旧候选。
- 生成期间禁用候选切换，不提供旧候选临时预览。
- 上一条／下一条按钮循环切换已有候选，不调用模型。新增候选仅通过独立的“重新生成”按钮触发。
- MVP 仅使用点击，不提供滑动手势。切到候选边界不能意外发起生成。
- 完整回复、主动停止和异常中断后的部分回复均保留；重新生成不会删除它们。
- 必须等后端确认上一生成已经完成或中断、不再输出后，才允许新生成。浏览器暂时没有收到文字不是完成证据。
- 末尾为用户消息时提供“生成回复”；末尾为 AI 时提供“继续”，新增一条 AI 消息，上一条内容保持不变，不向原候选末尾追加文字。
- 模型上下文只采用当前剧情中选中的候选，不将其他候选重复加入；选中空候选时仍传入 `{"role":"assistant","content":""}`，不自动省略。

### 4.2 编辑和删除

- 用户消息和 AI 历史消息均允许直接修订；提示后续内容不会重算，由用户判断剧情影响。
- 编辑采用原位文本框，保存后恢复显示。编辑会话不影响已经创建的独立分支。
- 多设备修改同一消息时采用最后保存覆盖，不引入强制冲突比较流程。
- 生成期间禁止修改当前会话上下文，该限制优先于最后保存覆盖规则。
- 删除历史消息会删除该消息及全部后续；执行前明确展示并确认删除范围。
- 支持删除末尾 AI 消息的单个候选，每次均确认；删除未选中候选不改变当前选择，删除当前候选则循环选择下一个，末项删除后回到首项。
- 允许删完全部候选；删除最后一个时明确提示同时移除该 AI 消息，相当于该层 AI 回复未发生过。这与“删除消息及其后续”是不同操作。
- 历史编辑未保存时，切换会话或点击跳转通知需提供保存、放弃、取消跳转。主动取消编辑后的草稿保留策略未确认。
- 本机正在编辑历史消息时，若另一设备启动生成，保留编辑文本并禁用保存；生成结束后才允许保存，并提示后续回复不会重算。

### 4.3 分支

- 用户主动选择“从这里分支”，复制为独立新会话，原会话完整保留；创建后立即进入新会话并定位到分支点，跳转仍遵守未保存编辑提示规则。
- 生成期间允许从已完成的历史消息分支；正在生成的消息需停止或结束后才允许分支。
- 新会话包含分支点及之前所有消息、所有历史 Swipe 和各消息当前选中的候选。
- 分支具有 deep copy 使用语义：两边之后的编辑、删除、候选生成与选择互不影响；不要求物理复制每份存储。
- 例如在用户第 10 条消息上分支，新会话保留至该条；用户可编辑它后重新生成后续。
- 在 AI 消息上分支，该 AI 消息成为新会话末尾，可切换保留下来的候选或请求新候选。

### 4.4 名称、列表与阅读位置

- 默认名称：`会话 YYYY-MM-DD HH:MM:SS`；分支追加 `Branch #%d`。
- 默认名称使用后端宿主机时区，生成后作为固定文本保存；底层时间戳保存 UTC。容器部署需明确宿主机时区的传入方式，不依赖容器偶然默认值。
- 分支编号按每个源会话独立递增，删除后不复用；从分支再次分支时以该分支作为新的源会话计数。
- 支持重命名、按名称搜索及整段会话删除。删除需确认；若仍在生成，先完成本地取消再删除；已创建的独立分支保留。
- 会话列表显示名称、最后时间、未读状态、正文结尾；正文结尾不是模型生成的摘要。
- 按消息活动时间排序并显示最后时间：发送、生成完成或中断（含停止）、编辑、删除、切换候选时更新；仅阅读不更新，流式输出不逐字重排。正文结尾片段长度留待原型确定。
- 仅 AI 任务结束（完成、失败或主动停止）触发未读；任一设备正前台查看该会话时视为已读。打开会话即清除未读，全账号同步；编辑或候选切换不触发未读。
- 按设备保存阅读位置；切走再返回或刷新后恢复原位置，有新内容时提供回到底部入口。

### 4.5 自有格式导入导出

- MVP 仅支持单个会话导出；分支与普通会话相同，不隐含导出其他关联会话。
- 导出保留全部消息、全部 Swipe、当前选中项及失败／停止状态。生成期间禁用导出，停止或结束后可导出。
- 导入始终创建独立新会话，不覆盖原记录；重名在末尾追加 `(1)`、`(2)` 等递增后缀。
- 聊天导入导出不承担服务器配置备份职责，API key 不得进入导出文件。文件版本、校验、大小限制和安全解析留待技术设计。

## 5. 生成生命周期与多设备

### 5.1 必须满足的行为

- 生成由后端持有。关闭页面、切换会话或浏览器断网不直接取消模型请求。
- 恢复连接后同步已保存文本与最新任务状态；已完成的回复应可查看。
- 不同会话允许并行生成；同一会话只允许一个生成任务。
- 任一登录设备可查看同一会话的生成并发出停止请求。
- 生成期间所有设备均不能再次发送或修改该会话上下文；允许提前编辑未发送草稿。
- 主动停止后保留部分回复并标记已停止，下次发送时将其作为当前回复纳入上下文。
- 应用崩溃允许最多丢失最后约 1 秒文字；恢复后保留已持久保存的内容并标记中断。供应商连接中断同样保留已接收内容并标记中断，不自动续写或重试。
- 不设应用层无输出超时，由用户停止或供应商／连接报错结束；后台实现不能暗中增加首字或流式闲置超时。
- 停止时由后端主动取消请求并停止接收输出；完成本地保存后标为已停止、解除会话锁，无需等供应商确认。该状态不承诺供应商已停止计算或计费。
- 不要求应用进程重启后恢复原供应商连接并无缝接着输出。
- 任务使用启动时配置快照；后续切换、编辑或删除连接配置不取消或改变已启动任务。

### 5.2 状态呈现

| 场景 | 界面行为 |
|---|---|
| 等待首字 | 在新 AI 消息处显示轻量动态圆点和“等待回复”，立即提供停止按钮 |
| 正在生成 | 仅更新当前生成内容，维持稳定排版；根据用户滚动状态决定是否跟随 |
| 主动停止 | 保留部分文本，明确标记已停止 |
| 生成异常 | 保留部分文本，标记中断并提供可理解的错误反馈，不自动重试 |
| 浏览器断线 | 持续显示不遮挡正文的“连接已断开，正在重连”，保留文本与草稿 |
| 连接恢复 | 自动同步内容和真实任务状态，不将断线误判为生成结束 |
| 其他会话完成 | 弹出可点击跳转的 toast，不自动切换当前会话 |

“停止请求已提交”与“本地取消和保存已完成”需要区分；取消尚未完成时不能启动新任务。具体等待与取消失败反馈留待交互及技术设计。

### 5.3 状态保存范围

| 状态 | 范围 |
|---|---|
| 会话、消息、候选和任务状态 | 后端持久保存，各设备读取同一份状态 |
| 未发送草稿 | 各设备按会话分别保存，刷新和切换后可恢复，不互相覆盖 |
| 阅读位置 | 按设备分别保存 |
| 当前连接配置及每套配置最后选择的模型 | 按设备独立，手机切换不改变电脑选中项 |
| 未读状态 | 账号全局同步，与设备阅读位置独立 |
| 外观偏好 | 账号全局同步 |
| 系统亮暗模式 | 全局选择“系统”后，各设备跟随自己的系统状态 |

## 6. 模型连接与上下文

- MVP 支持 OpenAI 兼容 Chat Completions（`/chat/completions`）；不将 Responses 或供应商特有能力纳入首版承诺。
- 连接配置继续在网页新增、编辑、删除和切换；配置选中项、每套配置最后选择的模型均按设备记忆。
- 尝试自动获取模型列表，同时始终允许手动填写模型 ID。
- 已选配置被其他设备删除时，提示重新选择后才能启动新生成；不自动切换到其他连接。已启动任务使用原快照，不受影响。
- API key 仅供后端调用，不进入前端持久存储、日志、聊天导出或版本库；管理界面脱敏呈现。
- MVP 默认总预算为 200,000 token，包含全部模型输入与最大输出预留；最大输出默认 8,000 token，因此输入最多为 192,000 token（含消息结构等开销，不能全当作正文额度）。
- 未来角色卡、预设、世界书形成的输入同样计入总预算；总预算和最大输出量远期由预设管理，MVP 不增加对应配置面板。
- 超预算自动省略最早消息，保留最近能容纳的内容；显示轻量提示并允许查看省略范围，完整聊天记录不删除。
- 用户接受早期普通消息中的角色设定可能被省略；不默认固定设定或自动摘要。
- 最新用户消息自身超过输入预算时阻止请求、保留文本并提示缩短，不静默截断。
- 200K 是应用预算，不保证兼容模型都能接受；供应商超限或不接受空 assistant 等请求时，提供明确错误，不自动收费重试或擅自改写内容。
- token 估算、模型未知时的计算策略、输出限制字段、裁剪消息边界与“继续”末尾超大 AI 消息的处理，留待技术设计及必要的业务补充；不得宣称跨模型精确计数已解决。

## 7. 页面与 UI/UX

### 7.1 聊天布局与导航

- 默认仅显示聊天主体，没有常驻会话侧栏或模型设置右栏。
- 会话列表以浮框打开，不挤压正文；手机同样使用居中浮框，四周保留少量留白，列表内部滚动。
- 连接配置与模型统一在“连接”入口管理，不在顶部放置独立模型选择框。
- 连接面板在桌面和手机均使用居中浮框、内部滚动；顶部信息与其他入口位置留待原型验证。

### 7.2 两种显示模式

| 模式 | 布局与用途 |
|---|---|
| 阅读式，默认 | 用户与 AI 卡片同宽、对齐，适合中文长篇 RP |
| 气泡式 | 用户靠右、AI 靠左，短消息收窄，长消息获得足够宽度 |

- 用户可切换模式，不改变消息内容与候选状态。
- 阅读式以同色系邻近底色区分用户与 AI；避免刺眼对比，也不能近似到难以分辨。
- 保留轻量身份标识，不仅依靠颜色表达来源。
- 长消息获得足够宽度不意味着默认折叠正文；是否需要折叠功能尚未讨论。

### 7.3 排版、主题与动效

- 提供舒适默认排版，仅开放字号与正文宽度调整，不增加行高、段间距或字体选择面板。
- 正文宽度必须受设备可用空间限制；全局同步设置不能造成手机横向溢出。
- 用户和 AI 内容使用标准 Markdown，动作描写采用斜体，控制标题与段落间距。
- 提供下表六套日本传统色主题，色名与基准色取自 [NIPPON COLORS — 日本の伝統色](https://nipponcolors.com/)。本决策替代早期原型方案中的三套配色；基准色用于建立主题色相，不要求直接用于所有按钮、文字或背景。

|---|---|---|---|
| 紅梅 | KOHBAI | `#E16B8C` | [紅梅](https://nipponcolors.com/#kohbai) |
| 黄朽葉 | KIKUCHIBA | `#D9AB42` | [黄朽葉](https://nipponcolors.com/#kikuchiba) |
| 松葉 | MATSUBA | `#42602D` | [松葉](https://nipponcolors.com/#matsuba) |

| 藤 | FUJI | `#8B81C3` | [藤](https://nipponcolors.com/#fuji) |

- 每套主题配备完整语义色板：页面背景、卡片／浮框、用户与 AI 消息底色、主次文字、边框／分隔线、输入框、主次按钮、链接、选中、悬停、按下、禁用、键盘焦点，以及成功、信息、警告、错误／危险操作等功能色。背景与交互色采用主题相近色相，通过明度与饱和度建立层级，不只替换主按钮颜色。
- 成功、信息、警告、错误等功能色采用与主题协调的色调，同时保持语义可辨识性；不能为追求同色相使成功与错误混淆。状态还须配合图标和文字，危险操作保留明确警示。
- 六套主题分别设计亮色和暗色色板，共十二套实际色板；暗色不使用简单反色，也不机械沿用亮色基准色。颜色通过现有组件语义 token 统一应用，避免组件内散落主题专用色值。
- 主题色与显示模式是独立设置。每套主题均提供“亮色”“暗色”“跟随系统”三选一，默认“跟随系统”；显式选择亮色或暗色时保持用户选择，跟随系统时首次加载读取本机系统偏好，并实时响应系统变化。未能读取系统偏好时使用亮色。
- 主题与显示模式选择按账号同步；“跟随系统”只同步该选择，各设备根据自己的系统偏好显示，不将一台设备解析出的亮暗结果同步覆盖其他设备。原型阶段使用当前浏览器本地保存模拟，不能据此宣称跨设备同步完成。
- 主题与亮暗切换不刷新页面、不丢失草稿、不重置候选或阅读位置；首屏初始化避免明显的亮暗闪烁。主题选项显示色名、色样和选中标识，不能仅靠色样区分。
- 各实际色板需检查正文、辅助文字、按钮、焦点与关键边界的对比度；调整用于交互的派生色，不强行将原始基准色用作低对比文字。最终派生色值、字体数值和默认主题色在原型视觉验证中确定。
- 界面使用短过渡、淡入淡出和轻微位移，不采用弹跳或导致正文反复移动的动效。
- 保留键盘焦点、可访问名称和非颜色状态标识；减少动态效果偏好应受到尊重。

### 7.4 流式显示与滚动

- 提供直接显示和平滑显示，默认平滑；只缓冲少量文字，不做长时间逐字排队。
- 后端原始文本与前端显示进度分离，保存、复制、编辑与分支基于真实内容，不以动画进度为准。
- 用户主动上滑后停止自动跟随，显示回到底部入口；回到底部后恢复跟随。
- 流式 Markdown、频繁换段、斜体和长历史不应造成明显跳动或反复重排整个历史。

### 7.5 输入、编辑与操作栏

- 桌面 Enter 发送、Shift+Enter 换行；手机回车换行、点击发送。
- 中文输入法候选确认不能误触发送。
- 手机输入框随内容增高至有限高度，随后内部滚动；可展开为全屏写作。
- 原位编辑历史消息，提供明确保存／取消动作，保存后恢复正文。
- 复制按钮仅复制原始 Markdown；MVP 不增加纯文本复制方式。
- 手机消息轻量操作栏直接显示复制与更多；会话末尾 AI 消息另外显示候选切换与重新生成。
- 更多操作承载编辑、分支和删除等能力，具体顺序与桌面显隐方式待细化。

## 8. 部署、认证与运行要求

- Docker 部署，面向 VPS 与浏览器访问；HTTPS 使用 Caddy。具体容器组合、证书接入和持久卷方案需技术验证。
- 服务器配置一次性初始化码，浏览器凭码创建唯一账号；成功后关闭初始化入口，不开放注册。支持多设备登录。
- 认证前不得暴露业务数据或凭据；初始化码不能绕过“唯一账号”约束，并发初始化、一次性消费须验证。
- 登录闲置有效期在服务器配置，默认连续 3 天未使用后过期。仅前台阅读或操作续期，后台心跳、重连及生成不续期；具体实现需验证可见性与会话语义。
- 忘记密码通过服务器命令重置，并使全部设备登录失效；网页仅支持退出当前设备，不提供退出全部设备入口。
- 部署、认证密钥及服务器备份在服务器管理，API 连接配置仍在网页管理。网页聊天导入导出不能替代完整备份恢复。
- 更新和重启不得丢失已保存会话；执行中的任务恢复为明确中断状态，故障文字损失遵守第 5 节承诺。
- 完整服务器备份的覆盖范围、命令、凭据密钥恢复与恢复演练方案尚待设计，不能因支持聊天导出而宣称灾难恢复完成。

## 9. 技术约束与待验证选型

用户再次确认前端基础为 [nuxt-shadcn-dashboard](https://github.com/dianprata/nuxt-shadcn-dashboard)，作为本项目对通用 Nuxt UI 优先规则的明确例外，不混用两套 UI 框架。实施前核对实际版本、依赖和许可证；本轮未进行代码或版本核验。

- 模板用于组件、设计系统和应用外壳，不将演示登录页或持久化依赖视为完成的业务能力。

- 选型需验证后台持续生成、断线恢复、多会话并行与移动端长文本体验，不能只以简单聊天演示作为依据。

## 11. 收敛评估与剩余决策

### 11.1 业务边界充分性与粒度

**结论：核心 MVP 业务边界已足以进入技术方案验证和交互原型阶段，但尚不构成无条件实施或完整验收基线。**

- 聊天操作、候选生命周期、分支隔离、多设备互斥、上下文预算、认证部署与内容迁移均已有明确范围；不再需要按页面逐项扩展产品功能。
- 空候选、删空、失败后的选中项、本地取消、编辑与生成冲突等细节会改变数据或用户输入，保留在 PRD 中粒度合适，应转化为状态转换及验收用例。
- 前期访谈已进入较细层级。颜色、字号数值、按钮位置、提示文案、片段长度等不继续逐项问卷化，交给原型验证；数据库、SDK、流式协议、token 算法等交给有依据的技术设计。
- 当前 MVP 仍属于中大型需求：后台持久任务、多端同步、长文渲染、认证与导入导出均需独立验证。聊天演示成功不足以证明可交付。
- 明确保留后续范围：角色卡、世界书、预设与 SillyTavern 兼容；本轮提及长期需求不将其自动纳入 MVP。

### 11.2 尚未回答的业务问题

以下没有用户决策，不得把问卷推荐选项当作批准：

1. 发送后何时清空输入草稿，以及服务端已接收但客户端未收到确认时如何避免输入丢失或重复发送。
2. 其他设备删除当前会话后，本机未发送草稿的保留、复制或迁移行为；被删除消息的未保存历史编辑同样需在相应实现前定义。
3. 主动取消历史编辑后的草稿策略，以及消息被其他设备删除后的保存反馈。

这些是局部交互阻塞项，应在对应实现批次前集中确认，不妨碍先验证架构与原型。其他未定行为若影响用户数据或契约，必须明确记录，不能通过实现默默决定。

### 11.3 技术设计必须解决

- 后端、数据库、持久任务、流式同步与重启恢复；约 1 秒损失承诺、本地取消后的迟到输出隔离、重复请求去重及多设备原子互斥。
- 兼容接口实际字段与 token 估算；200K/8K 预算的计算误差、消息边界裁剪、单条超大 AI 的继续行为；供应商错误反馈。采样参数和并发资源上限尚未选定。
- 成熟认证库与指定模板的集成验证；单账号初始化、闲置会话判定、密码重置全端失效；Caddy、时区、密钥管理与服务器完整备份恢复。
- 自有格式版本、导入校验与事务性、恶意内容处理、文件上限；不得把聊天迁移当作认证或连接配置迁移。
- 50 × 8K token 长历史的加载、Markdown、滚动与性能阈值，桌面和移动 Chrome 实测环境。

### 11.4 原型阶段细化

- 顶部信息、设置及消息操作入口、错误与取消等待反馈、正文结尾片段、浮框焦点和返回行为。
- 六套日本传统色的亮暗派生色板、各功能色、默认主题色、字号与宽度范围、平滑输出效果；主题数量、基准色及默认跟随系统已由第 7.3 节确认，不再列为待决项。长文折叠未纳入已确认功能。
- 无会话、无连接、模型列表失败、导入失败、跨设备删除等关键空态与错误态。
